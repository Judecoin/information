지갑 다운로드

보안 센터

보호 지갑, 키, 서버 접근, 및 서비스 노드 신원.

서비스 노드 운영은 스테이킹하고 서버를 시작하는 것만을 의미하지 않습니다. 운영자는 자금, 인프라, 노드 신원을 안전하게 복구할 수 있도록 지갑 복구 정보, 개인 키, 접근 파일, 노드 기록, 백업 자료도 보호해야 합니다.

중요 보안 자료

지갑 복구, 서비스 노드 식별, 서버 접근에 사용될 수 있는 자료를 보호하세요.

01

지갑 시드 문구 백업

지갑 시드 문구는 가장 중요한 복구 도구 중 하나입니다.

  • 시드 문구를 누구와도 공유하지 마세요
  • 시드 문구를 채팅 앱이나 이메일로 보내지 마세요.
  • 온라인 컴퓨터에 시드 문구를 평문으로 저장하지 마세요.
  • 시드 문구의 스크린샷을 찍지 마세요.
  • 시드 문구를 클라우드 저장소에 업로드하지 마세요.
  • 시드 문구를 알 수 없는 웹사이트나 도구에 붙여넣지 마세요.
  • 최소 하나의 오프라인 백업을 안전한 장소에 보관하세요.

지갑 시드 문구를 잃어버리면 지갑을 복구하지 못할 수 있습니다. 시드 문구가 유출되면 지갑 자금이 위험해질 수 있습니다.

02

지갑 비밀번호 백업

지갑 비밀번호도 중요합니다.

  • 강력한 비밀번호를 사용하세요.
  • 단순한 비밀번호를 사용하지 마세요.
  • 지갑 비밀번호를 시드 문구와 함께 보관하지 마세요.
  • 지갑 비밀번호를 누구에게도 보내지 마세요.
  • 필요한 경우 안전한 오프라인 백업을 보관하세요.

지갑 시드 문구와 지갑 비밀번호는 서로 분리해 보관하는 것이 좋습니다.

03

서비스 노드 비공개 키 백업

서비스 노드 개인 키는 서비스 노드를 식별하는 데 사용됩니다. 키 파일은 일반적으로 /home/ubuntu/.bitjudecoin/key_ed25519 위치에 있습니다.

  • 서비스 노드 개인 키를 공유하지 마세요.
  • 채팅 앱이나 이메일로 보내지 마세요.
  • 공개 그룹에 게시하지 마세요.
  • 공개 클라우드 저장소에 업로드하지 마세요.
  • 보관하다 에서 최소 둘 오프라인 백업
  • 백업은 서로 다른 안전한 장소에 보관하세요.

서버를 분실하거나, 손상되거나, 재설치하거나, 이전하는 경우 원래 서비스 노드 신원을 복구하기 위해 서비스 노드 개인 키가 필요할 수 있습니다.

04

.pem 서버 접근 파일 백업

.pem 파일은 서버에 접근하는 데 사용됩니다. .pem 파일을 잃어버리면 정상적인 SSH 서버 접근이 불가능해질 수 있습니다.

  • .pem 파일을 누구와도 공유하지 마세요.
  • 공개 저장소에 업로드하지 마세요.
  • 한 대의 컴퓨터에만 보관하지 마세요.
  • 암호화된 오프라인 백업을 보관하세요.
  • 혼동을 피하기 위해 명확한 파일 이름을 사용하세요.
  • 여러 노드를 관리하는 경우 서로 다른 서버 키를 신중하게 보관하세요.

.pem 파일은 민감한 접근 파일로 취급해야 합니다.

백업 및 복구 구조

지갑과 서비스 노드 복구가 단일 기기에 의존하지 않도록 백업과 비공개 기록을 분리해 보관하세요.

05

서버 정보 백업

서비스 노드 운영자는 서버 정보에 대한 기본적인 비공개 기록을 보관해야 합니다.

  • 서버 지역
  • 서버 제공업체
  • 인스턴스 이름
  • 공개 이프 주소
  • CLI 버전
  • 서비스 노드 공개 키
  • 지갑 사용됨 위한 등록
  • 등록 드아트에
  • 현재 노드 상태
  • 업그레이드 또는 재시작 관련 메모

이 전체 기록을 공개적으로 게시하지 마세요. 이 기록은 비공개 관리와 복구에 유용합니다.

06

권장 백업 구조

중요한 파일은 한 곳에만 존재해서는 안 됩니다.

  • 중요 파일의 일상 백업을 위한 기본 암호화 USB 드라이브
  • 별도로 보관하고 드물게만 연결하는 오프라인 암호화 USB 드라이브
  • 시드 문구와 같은 필수 복구 정보를 위한 종이 백업
  • 서버 지역과 서비스 노드 공개 키를 위한 비공개 노드 기록 파일

분리된 백업 구조는 단일 기기 고장이나 접근 문제로 인한 위험을 줄입니다.

07

하드웨어 암호화 USB 드라이브

하드웨어 암호화 USB 드라이브는 민감한 파일을 보관하는 데 유용할 수 있습니다.

  • 서비스 노드 비공개 키 백업
  • .pem 파일 백업
  • 노드 기록 파일
  • 지갑 복구 노트
  • 중요한 운영 문서
  • 암호화된 USB 드라이브를 최소 두 개 사용하세요.
  • 서로 다른 안전한 장소에 보관하세요.
  • 두 백업을 같은 가방이나 같은 컴퓨터에 보관하지 마세요.
  • 백업에 의존하기 전에 USB 드라이브를 테스트하세요.
  • 비밀번호는 안전하게 보관하고 USB 드라이브와 분리하세요.

암호화된 백업은 백업 장치와 비밀번호가 모두 보호될 때만 의미가 있습니다.

이 자료는 절대 공유하지 마세요

복구 자료, 개인 키, 접근 파일, 민감한 스크린샷은 공개 또는 비공개 채널로 보내지 않아야 합니다.

08

무엇 해야 합니다 절대 이다 공유

절대 공유하다 민감한 지갑, 서버, 또는 서비스 노드 접근 정보.

  • 지갑 시드 문구
  • 지갑 비공개 키
  • 지갑 비밀번호
  • 브이에워 키
  • 지출 키
  • 지갑 파일
  • 서비스 노드 비공개 키
  • .pem 파일
  • 서버 로그인 자격 증명
  • 인증 코드
  • 민감한 정보가 포함된 백엔드 스크린샷

누군가 이러한 자료를 요구한다면 심각한 보안 위험으로 간주하세요.

커뮤니케이션 및 커뮤니티 안전

공개 채널, 이메일, 스크린샷, 기여 워크플로에서 피할 수 있는 노출을 줄이세요.

09

이메일 및 피싱 안전성

프로젝트, 커뮤니티, 기술팀을 대표한다고 주장하는 이메일이나 메시지에 주의하세요.

  • 발신자가 신뢰할 수 있는 도메인을 사용하는지 확인하세요.
  • 메시지가 개인 키나 시드 문구를 요구하는지 확인하세요.
  • 의심스러운 링크가 있는지 확인하세요.
  • 메시지가 긴박감을 조성하려는지 확인하세요.
  • 응답하기 전에 신뢰할 수 있는 프로젝트 채널을 통해 신원을 확인하세요.

절대 제공하다 개인 키, 시드 문구스, 지갑 파일, 또는 서버 접근 파일 통해 이메일.

10

GitHub 및 커뮤니티 안전성

GitHub Discussions나 문서에 기여할 때 비공개 운영 정보를 노출하지 않도록 주의하세요.

  • 지갑 시드 문구를 게시하지 마세요.
  • 서비스 노드 개인 키를 게시하지 마세요.
  • .pem 파일을 게시하지 마세요.
  • 서버 로그인 정보를 게시하지 마세요.
  • 전체 백엔드 스크린샷을 게시하지 마세요.
  • 공유하기 전에 스크린샷에서 개인 정보를 제거하세요.
  • 대규모 보유량이나 노드 소유 세부 정보를 공개적으로 노출하지 마세요.

커뮤니티 기여는 유용해야 하지만, 비공개 운영 정보를 노출해서는 안 됩니다.

마이그레이션 및 복구 준비

서버를 변경하거나, 자금을 이동하거나, 서비스 노드 신원을 복구하기 전에 복구 자료를 확인하세요.

11

전에 서버 므이그르아트이오느 또는 복구

노드를 이전하거나 복원하기 전에 필요한 접근 자료와 신원 자료가 준비되어 있는지 확인하세요.

  • 서비스 노드 비공개 키 백업
  • .pem 파일 또는 새 서버 접근 권한
  • CLI 버전 정보
  • 서비스 노드 공개 키
  • 노드 기록
  • 지갑 접근
  • 안전한 작업 환경

서비스 노드 개인 키가 올바른지 확실하지 않다면 복구 작업을 시작하지 마세요.

기본 백업 체크리스트

서비스 노드를 실행하거나 유지보수하기 전에 이 최종 체크리스트를 사용하세요.

12

기본 백업 체크리스트

서비스 노드를 실행하거나 유지보수하기 전에 필수 복구 자료가 백업되어 있는지 확인하세요.

  • 지갑 시드 문구
  • 지갑 비밀번호
  • 지갑 파일 만약 필요함
  • 서비스 노드 비공개 키
  • .pem 파일
  • 서버 지역 및 인스턴스 메모
  • 서비스 노드 공개 키
  • CLI 버전 정보
  • 노드 운영 노트
  • 기본 암호화 백업 하나
  • 하나 오프라인 암호화된 백업
  • 하나 분리 종이 백업 위한 크르이트이크아르 복구 정보

서비스 노드 보안은 서비스 노드 운영만큼 중요합니다.

결론

노드 운영자는 노드를 시작, 재시작, 복원하는 방법뿐 아니라 노드 뒤에 있는 키와 파일을 보호하는 방법도 알아야 합니다. 더 안전한 백업 습관은 피할 수 있는 위험을 줄이고 Service Node의 장기 운영을 보호하는 데 도움이 됩니다.
